## Context

现有 `next_day_study_reminder` 在 `SubscribeMessageGrant` 中使用单个 `scheduledSendDate` 与 `availableCount=1`。用户通常在晨读开始前后进入小程序；主发送改为 05:55 后，用户点击入口与今日发送可能并发。若仍仅按总库存判断，要么不会补充明日，要么会覆盖今日计划。

## Goals / Non-Goals

### Goals

- 两个晨读入口均能在用户点击中合规请求订阅授权。
- 以“期次 + 明日日期”判断是否需要补充。
- 允许今日待发和明日已授权同时存在。
- 05:55 发送且在主任务、重试和授权并发时不重复、不丢失。

### Non-Goals

- 不改变微信订阅模板、模板字段或点击目标页。
- 不为用户一次预约多天通知。
- 不改变评论、点赞等其他订阅场景的补量目标。
- 不执行数据库重置或破坏性迁移。

## Decisions

### 1. 共用明日通知请求入口

两个页面调用同一个明日通知补充帮助函数，仅传入 `next_day_study_reminder`、`periodId`、`sectionId`、`sourcePage` 和 `sourceAction`。请求完成后无论结果都继续原跳转。

### 2. 按目标日期而非总库存判断

授权状态返回当前和排队的日期、期次以及次日是否在期次范围。前端只在目标明日尚未存在且仍在期次范围时请求。本地单日节流、全局 `inFlightPromise` 和服务端日期幂等共同去重。

### 3. 使用现有记录的双日期槽

保留 `scheduledSendDate*` 作为最早待发项，新增可空的 `queuedSendDate*`、`queuedPeriodId` 和 `queuedContext` 作为紧随其后的明日项。最多两个槽位足以覆盖 05:55 前后的今日/明日交接，且不引入新集合。

今日发送成功后，通过以当前日期为条件的原子更新提升排队槽。无排队项时才清空当前计划。对新请求的拒绝不能清理旧的已接受槽位。

### 4. 发送原子领取与幂等

在实际调用微信前，发送器按 grant ID、当前日期、到期状态和未被领取条件原子标记。同一 `sourceId=<userId>:<periodId>:<sendDateKey>` 已成功投递时直接跳过。领取失败的 worker 不投递。

### 5. 05:55 主发与 06:00 重试

计划时间和主 cron 均为 05:55，不改模板中展示的课程开始时间 06:00。06:00 起对已标记为可重试的项执行最多一次重试。原子领取确保主发尚在处理时重试不会并发投递。

## Error Handling

- 订阅状态或授权保存失败：记录警告并继续跳转。
- 用户 `reject`/`ban`：记录请求结果，保留既有待发日期；后续按微信设置决定是否再提示。
- 期次或日期无效：不请求授权，不创建队列项。
- 发送临时失败：保留授权并排队一次重试。
- 非可重试微信错误：按现有规则停止该日投递，不损坏已排的下一日。

## Migration Plan

1. 先部署兼容旧字段的后端模型和发送逻辑。
2. 再发布两个小程序触发入口和 05:55 文案。
3. 观察授权结果、当前/排队日期、发送成功和幂等跳过日志。
4. 回滚时先停止前端新触发，旧后端仍可忽略新的可空字段。

## Risks / Trade-offs

- 授权记录增加一个排队槽，比单次库存复杂，但它是在不引入新集合的情况下正确处理 05:55 并发窗口的最小结构变更。
- 跳转前多一次订阅状态查询；使用现有短时缓存和进行中请求合并控制延迟。
- 微信授权由用户决定，系统只能保证请求时机和已接受授权的可靠投递，不能保证拒绝用户收到通知。
