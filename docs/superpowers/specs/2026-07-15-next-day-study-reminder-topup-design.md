# 明日开课通知按日补充设计

## 目标

已报名且有学习权限的用户从首页点击“去晨读”，或从课程详情点击“进入沉浸阅读”时，系统尝试为该期次的次日课程补充 1 次“明日开课通知”授权。通知于北京时间 05:55 主发，让用户更容易返回当日晨读。

## 触发与用户体验

- 首页普通“去晨读”和时间提示弹窗中的“去晨读”共用 `handleJoinMeeting`，在该方法内统一触发。
- 课程详情的“进入沉浸阅读”在 `handleImmersiveReading` 内触发。
- 只请求 `next_day_study_reminder` 模板，不与评论、点赞等授权混合。
- 次日已有可用授权时直接跳转，不弹窗。同一用户在两个入口之间往返也不重复请求。
- 最后一天或次日不在期次范围时不请求授权。
- 用户拒绝、禁用、关闭弹窗，或前后端调用失败时，仍继续进入沉浸阅读，通知失败不阻断主流程。

## 日期化授权队列

现有 `SubscribeMessageGrant` 把授权库存和单个发送日绑在一起。当用户在 05:55 附近进入晨读时，今日通知可能尚未消耗，不能用简单的 `availableCount < 1` 判断明日是否已补充。

保留现有当前发送字段，在同一授权记录上增加一组“已排队的次日发送”字段：

- `queuedSendDate`
- `queuedSendDateKey`
- `queuedPeriodId`
- `queuedContext`

授权成功时按目标日期处理：

1. 当前和排队槽均无该日期：无当前发送则写入当前槽；今日发送仍待处理则写入排队槽。
2. 任一槽已有相同期次和日期：保持幂等，不再增加库存。
3. 今日通知发送成功：只消耗今日的 1 次授权；如存在排队槽，原子提升为当前槽。
4. 新一次授权被拒绝：不清空已经存在的今日发送，避免破坏之前已获得的授权。

队列最多保留“今日 + 明日”两个日期，不预约更多天，避免超出“每次晨读补明天一次”的范围。

## 发送与并发保护

- 次日计划时间、主 cron、页面文案和测试期望统一从 05:45 改为 05:55。
- 06:00 起保留最多一次短暂失败重试。
- 发送前对“用户 + 期次 + 发送日”做原子领取，同一日期同时只允许一个 worker 投递。
- 订阅消息仍以现有 `sourceId=<userId>:<periodId>:<sendDateKey>` 作为幂等业务键，已发送的键不再重复投递。
- 仅 PM2 `NODE_APP_INSTANCE=0` 运行该调度，保留现有多实例边界。

## 兼容与迁移

- 新字段均为可空字段，旧记录继续使用现有当前发送字段，不需要数据库初始化、清空或破坏性迁移。
- 发送成功后的“清空”操作改为“提升排队项，否则清空”，保持旧数据行为不变。
- 租户模板 ID 、微信字段映射和通知跳转页面不变。

## 测试

- 小程序：两个入口均只请求明日通知；已排明日时不弹；拒绝或错误仍跳转；最后一天不弹；首页时间弹窗入口同样生效。
- 后端：无当前项时写入明日；今日待发时排队明日；重复授权幂等；拒绝不删今日；成功后提升明日；期次越界不请求。
- 调度：05:55 到期发送；06:00 短暂失败可重试；主任务与重试重叠时不重复发送。
- 回归：评论、点赞等其他订阅场景仍按现有目标库存逻辑工作。
